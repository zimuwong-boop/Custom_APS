# 演示操作复核（2026-10-11）

## 检查对象与结论

读取用户操作后的 Docker 数据库一致性快照，在独立临时 SQLite 副本上模拟后续操作，运行中的演示库未被修改。采样时已有 15 张正式生产单、12 条依赖边；底层 LOW / NORMAL / HIGH 批次自身进度分别为 35% / 97% / 100%，HIGH 瓶装批次自身进度为 50%。

当前状态及本次模拟范围内未发现业务数据、进度传播或追溯错误。这是已执行场景的结论，不代表所有可能操作均无缺陷。

## 当前进度独立核对

所有非底层订单的子单贡献比例为 60%。

| 优先级 | 底层半成品 | 瓶装批次总进度 | 包装成品总进度 |
|---|---:|---:|---:|
| LOW | 35% | 21% | 12.6% |
| NORMAL | 97% | 58.2% | 34.92% |
| HIGH | 100% | 80%（自身50%） | 48% |

未达到开工条件的父单可以显示子单贡献进度，但自身进度仍为零，状态为 WAITING；这符合已约定的规则。销售单以各个不重复顶层批次等权计算，直接销售半成品会使该半成品同时成为销售根。

## 实际模拟

- 对 11 张 WAITING 生产单分别尝试开工和写入自身进度，全部返回 409，版本、进度事件及审计均未改变。
- 对已有下游开工使用的 HIGH 底层批次尝试回退，返回 409。
- 按依赖顺序继续完成所有订单，共执行 25 次合法开工/进度操作，每步执行完整性检查。
- 重放相同幂等请求得到相同结果；另一个请求使用旧版本被拒绝。
- 最终 15 张生产单和 20 张销售单均为完成状态，销售进度均为 100%。
- 完成后逐一查询 20 张销售单的追溯接口，均返回带有效批次号的生产节点。

机器结果：[当前状态模拟报告](simulation-current-report.json)。这些完成状态只存在于临时副本，未覆盖用户的演示进度或初始备份。

## 发现并修复的测试问题

原浏览器测试后端占用 8000 端口，演示容器运行时 `make e2e` 因端口冲突退出。未复用正在演示的服务，避免测试写入实际业务库。

已将隔离测试后端改为 18081、前端改为 15173，并配置对应代理及 CSRF 来源；日常开发仍使用原端口。相关文件：[浏览器配置](../frontend/playwright.config.ts)、[临时服务器](../scripts/e2e_server.py)、[开发代理](../frontend/vite.config.ts)。

修复后 3 项 Chromium 用例通过（19.9 秒），覆盖物料表单、销售确认、排产拆合、36% 依赖门槛、完成及批次追溯。这些浏览器用例使用独立抽象测试夹具；对当前蒜蓉酱快照的 25 次后续操作由实际 API 模拟执行。

`make check` 通过：50 项 Python 测试、5 项前端单元测试，代码检查、类型检查、生产构建、迁移检查及 Django 系统检查通过。

## 新增 LOW 订单的实际运行库实验

用户另行授权在当前系统实际新增并完成一张销售单。本次通过正式 HTTP API 执行与手工按钮相同的业务动作，并非浏览器点击模拟。

- 新销售单 `TEST-LOW-F87BC090`（ID 21）：A 包装蒜蓉酱 2 包装，默认及行有效优先级 LOW。
- 尝试给现有正式计划 ID 20 的 LOW 成品节点追加销售分配，返回 HTTP 409 / STALE_PLAN。正式计划已冻结，不允许原地增量修改；已有子单进度不代表可用于未分配的新销售需求。
- 新草稿 ID 21 保持全节点 LOW，手工将成品拆为 1+1，再合并为 2，随后确认生成独立的三层批次。
- 新父单在子单完成前开工仍返回 409；依次手工开工及更新自身进度至 100%，完成半成品、瓶装、包装三层。
- 新销售单最终 PRODUCTION_COMPLETED / 100%，追溯三个 `P20261011-000002` 批次，全程未改变 LOW 优先级。
- 原 15 张生产单的序列化字段未因本次实验改变，初始备份未覆盖；实际系统保留本次新增已完成销售单及三个生产批次，销售单现共 21 张。

优先级在本期用于合并分组，不是禁止手工优先完成 LOW 的执行门槛。允许操作员在子单满足依赖后先完成 LOW，而不要求 HIGH / NORMAL 先完成。若需要向已确认的在制批次追加新需求，这是当前冻结模型之外的变更需求，本次没有绕过数量守恒或冻结规则实现追加。
